# リファクタリング計画: Scrapbox Diary Launcher

> この文書は完了済みの初回改修計画を保存した履歴資料です。Wiki移行に関する記述は、2026年9月10日の旧Wiki文書廃止決定より前の計画であり、現行要件ではありません。現在の仕様は [機能仕様書](./functional-spec.md) を参照してください。

## 1. 目標

旧 `RedirectPage` プロジェクトを、`scrapbox-diary-launcher` という一貫性のある静的アプリケーションへリファクタリングします。

現在、次の場所に分散しているロジックをアプリケーションに集約します。

- Scrapbox側のリンク／UserScript
- Windowsスタートアップスクリプト／BATファイル
- リダイレクト用HTMLページ
- 重複するJavaScriptファイル

最終的には次の構成を目指します。

```text
Scrapbox UserScript ─┐
ブックマーク／URL ───┤
PowerShell／BAT ─────┼──> Scrapbox Diary Launcher ───> Scrapbox
Windowsスタートアップ ─┘
```

呼び出し元は単純に保ちます。日付ロジック、Scrapboxのページ名ロジック、本文生成、ランチャー生成は、このリポジトリ内に置きます。

## 2. 最初に確認する既存動作

ファイルの中身を確認せず、一律に置き換えるところから始めないでください。

まず、特に次の既存実装を確認してください。

- `Scrapbox/Diary/CreateToday/`
- `Scrapbox/Diary/ShowToday/`
- `Scrapbox/Diary/CreateMonthSchedule/`
- `Scrapbox/Diary/ShowMonthSchedule/`

現在の実装には次の機能が含まれていることが分かっています。

### CreateToday

- `project_url` を受け取る
- 任意の `yymmdd` を受け取る
- 任意の `body` を受け取る
- 日付を省略した場合は今日を使用する
- `YYMMDD` という名前の日次Scrapboxページへリダイレクトする

### ShowToday

- `project_url` を受け取る
- 任意の `yymmdd` を受け取る
- 日付を省略した場合は今日を使用する
- `YYMMDD` という名前の日次Scrapboxページへリダイレクトする

### CreateMonthSchedule

- `project_url` を受け取る
- 任意の `yymm` を受け取る
- 省略した場合は現在の月を使用する
- 次を含む月次ページ本文を生成する
  - 前月／翌月へのリンク
  - 月の見出し
  - 各日の日次ページへのリンク
  - `#月予定表`
- `YYMM` という名前の月次Scrapboxページへリダイレクトする

### ShowMonthSchedule

- `project_url` を受け取る
- 任意の `yymm` を受け取る
- 省略した場合は現在の月を使用する
- `YYMM` という名前の月次Scrapboxページへリダイレクトする

変更前にソースコードから実装を直接確認してください。

## 3. 必須アーキテクチャ

### 3.1 統合ランチャー

正規のランチャーエントリーポイントを1つ作成します。リポジトリルートの `index.html` を推奨します。

アクションごとの独立実装ではなく、小さなルーティング層を1つ使用してください。

公開インターフェースとしては次の形式が妥当です。

- `action=show-today`
- `action=create-today`
- `action=show-month`
- `action=create-month-schedule`

Scrapboxプロジェクト識別子には `project` パラメーターを使用してください。値がプロジェクト名またはslugにすぎない場合、`project_url` と呼ばないでください。

新しいURLでは読みやすいISO形式の日付入力を優先してください。

- 日次: `date=YYYY-MM-DD`
- 月次: `month=YYYY-MM`

省略した場合は、ブラウザーの現在のローカル日付／月を使用します。

旧形式の `yymmdd`／`yymm` は、互換ラッパーに役立つ場合に限り対応を維持してください。

### 3.2 本文の受け渡し

新しいランチャーでは、避けられる場合、自由記述の `body` をGitHub Pagesのクエリ文字列に含めないでください。

フラグメントで渡すことを優先します。

```text
?action=create-today&project=PROJECT#body=ENCODED_TEXT
```

クライアント側で解析し、最終的なScrapboxの遷移先に合わせてURLエンコードしてください。

これはScrapboxから本文を秘密にするものではありません。中継するGitHub PagesホストへのリクエストURLに、本文を不必要に含めないためのものです。

### 3.3 `project` を必須にする

旧実装では `Rutile3-Test` が既定値になっている可能性があります。新しい正規ランチャーでは、この暗黙のフォールバックを維持しないでください。

新しいインターフェースでは `project` を明示的に指定する必要があります。指定がなければテストプロジェクトへリダイレクトせず、小さなエラー／ヘルプページを表示してください。

### 3.4 互換ラッパー

改名後のリポジトリでも、既存の4つのHTMLエンドポイントパスを維持してください。可能な限り、薄いラッパーまたはアダプターへリファクタリングします。

次のような旧パラメーターを、新しい正規ランチャーのインターフェースへ変換してください。

- `project_url`
- `yymmdd`
- `yymm`
- `body`

ラッパー内に日付ロジックや業務ロジックを重複させないでください。

重要: これにより、新しいリポジトリ内の旧パスは維持できますが、リポジトリパスに `/RedirectPage/` を含む旧GitHub Pages URLの問題は解決しません。

## 4. GitHub Pages改名への移行

リポジトリはすでに `RedirectPage` から `scrapbox-diary-launcher` に改名されています。旧プロジェクトサイトURLは壊れている可能性があるものとして扱ってください。

### 必須作業

1. 可能な場合、リポジトリ設定や環境から新しいPagesのベースURLを特定する
2. 次の文字列がハードコードされていないかリポジトリを検索する
   - `/RedirectPage/`
   - `RedirectPage`
   - 旧Pages URL
3. 外部の呼び出し元でベースURLの更新が必要であることを文書化する
4. `docs/MIGRATION.md` などの移行ドキュメントを用意する
5. CreateToday、ShowToday、CreateMonthSchedule、ShowMonthScheduleについて新旧URL例を記載する
6. 代替の `RedirectPage` リポジトリを自動作成しない

移行ガイドでは、このGitリポジトリ内には通常存在しない次の外部更新箇所を明示してください。

- Scrapbox UserScript
- Windowsスタートアップ用BAT／PowerShellファイル
- ブックマーク／ショートカット

後述のツールジェネレーターにより、これらの呼び出し元を容易に置き換えられるようにしてください。

## 5. ランチャージェネレーターUI

ルートページには、ランチャー連携を作成するための簡単な利用者向けジェネレーターも用意してください。これは今回のリファクタリングを行う主要な理由の1つです。

### 入力

最低限、次の項目を用意してください。

- Scrapboxプロジェクト
- アクション
- 任意の日付／月の上書き指定
- 必要な場合に使用する任意の本文／テンプレートテキスト

小さく分かりやすいUIにしてください。フロントエンドフレームワークを追加しないでください。

### 生成する出力

最低限、コピー可能な次の出力を生成してください。

1. 正規ランチャーURL
2. Scrapbox UserScript／JavaScriptスニペット
3. PowerShellコマンド／スクリプト
4. BAT互換ランチャー
5. 簡単に対応できる場合はブックマーク用URL（任意）

各出力ではパラメーターを正しくエンコードしてください。

本文や複雑なエスケープを扱うWindows向けの例ではPowerShellを推奨してください。利便性と互換性のためBAT出力も提供してください。

ユーザーの業務予定やその他の非公開テキストをリポジトリへ埋め込まないでください。ジェネレーターはブラウザーの実行時に限ってそのようなテキストを受け取ります。

## 7. Wikiの移行

現在のREADMEは、詳細な使用方法についてGitHub Wikiを参照しています。Wikiをこのリポジトリ内へ移行してください。

### 取得

GitHub Wikiは独立したGitリポジトリです。次のURLから取得を試みてください。

```text
https://github.com/Rutile3/scrapbox-diary-launcher.wiki.git
```

メインリポジトリは改名されているため、ファイル名を推測せず、Wikiの実際の状態を確認してください。

現在の環境でWikiを取得できない場合はドキュメントを創作しないでください。阻害要因を記録し、コードのリファクタリングはレビュー可能な状態で残してください。

### 変換

すべての移行元Wikiページについて次を行ってください。

1. 元の内容をMarkdownとして保持する
2. `docs/wiki/` 配下へ配置する
3. 可搬性に必要な場合に限りファイル名を正規化する
4. Wiki形式の内部リンクを相対Markdownリンクへ修正する
5. `docs/wiki/README.md` を作成する
6. 元のページタイトル／ファイル名と移行先ファイルの対応表を記載する

忠実な複製を作成した後、古い `RedirectPage` アーキテクチャを説明するドキュメントを更新してください。

新しいジェネレーターがあるという理由だけで、古い使用方法を暗黙に削除しないでください。

### README

`README.md` を書き直し、次を説明してください。

- `scrapbox-diary-launcher` とは何か
- 存在理由
- 対応アクション
- ジェネレーターの使用方法
- URLパラメーターのリファレンス
- `body` に関するセキュリティ／プライバシー上の注意
- `RedirectPage` からの移行
- リポジトリ内ドキュメントへのリンク

重要なドキュメントがGitHub Wikiへ依存しないようにしてください。Wikiをリモートから削除しないでください。

## 8. URLの動作

### 日次ページ

Scrapboxの遷移先:

```text
https://scrapbox.io/{project}/{YYMMDD}
```

作成または事前入力用の本文を指定した場合:

```text
https://scrapbox.io/{project}/{YYMMDD}?body={encodedBody}
```

### 月次ページ

Scrapboxの遷移先:

```text
https://scrapbox.io/{project}/{YYMM}
```

### 月間予定の本文

不具合が見つからない限り、現在の意味を維持してください。次を確認してください。

- 前月へのリンク
- 翌月へのリンク
- `20YY年MM月` のようなタイトル
- 各日へのリンク
- 曜日のテキスト
- 最後の `#月予定表`

月や年をまたぐ境界を正しく処理してください。

## 9. 日付処理

「今日」にはブラウザーのローカル日時を使用してください。

UTC変換によって日付がずれる可能性のある、曖昧な日付文字列の解析を避け、入力を厳密に検証してください。

代表的なケース:

- 通常の日付
- うるう日
- 月末
- 12月から1月への移行
- 1月から12月への移行
- 2月30日などの無効な日付

新しいインターフェースでは次の形式を使用します。

- `YYYY-MM-DD`
- `YYYY-MM`

互換コードでは旧来の短縮形式を受け付けても構いません。

## 10. セキュリティとプライバシー

このプロジェクトは公開され、GitHub Pagesでホストされます。

コミットするファイルに次を含めないでください。

- 業務予定
- 顧客名
- 内部URL
- 認証情報
- トークン
- 非公開のScrapboxコンテンツ

ユーザー指定の本文は実行時にのみ存在するようにしてください。中継するランチャーURLでは本文をフラグメントで渡すことを優先してください。

解析機能や外部テレメトリーを追加しないでください。明示的に承認されない限り、サードパーティーCDNへ依存しないでください。

## 12. 実装順序

リポジトリ調査によってより安全な順序が判明した場合を除き、次の順序で進めてください。

### フェーズ1: 棚卸し

- `git status`
- ソースツリーを確認する
- 現在のREADMEを確認する
- Pagesに関する前提を確認する
- 既存エンドポイントを一覧化する
- 可能ならWikiを取得して一覧化する
- 旧リポジトリ名／Pages URLを検索する

### フェーズ2: ドキュメントの保存

- Wikiを忠実に `docs/wiki/` へ移行する
- 忠実な複製ができる前に内容を現代化しない

### フェーズ3: 共有コア

- 日付ロジックを抽出する
- パラメーター解析を抽出する
- Scrapboxの遷移先構築を抽出する
- 月間予定本文の生成を抽出する

### フェーズ4: 正規ランチャー

- ルートランチャーを実装する
- エラー／ヘルプ表示を実装する
- フラグメントによる本文処理を実装する

### フェーズ5: 互換性

- 旧エンドポイントを薄いアダプター／ラッパーへ変換する
- 可能な範囲で旧パラメーターを維持する

### フェーズ6: ジェネレーターUI

- URLジェネレーター
- UserScriptジェネレーター
- PowerShellジェネレーター
- BATジェネレーター

### フェーズ7: ドキュメント

- README
- 移行ガイド
- パラメーターリファレンス
- Wikiリンクの移行

### フェーズ8: 検証

- チェック／テストを実行する
- diffを確認する
- 非公開のユーザーデータがコミット対象にないことを確認する
- 未解決の移行作業をまとめる

## 13. 完了条件

次の状態になったとき、リファクタリングは完了です。

- 1つの正規ランチャーがコアロジックを担う
- 重複するリダイレクト／日付ロジックが削除されるか、互換ラッパーに限定される
- 既存の4機能が引き続き動作する
- 新しいURLが明確なパラメーター体系を使用する
- `project` が明示的に指定される
- 自由記述の本文をURLフラグメントでランチャーへ渡せる
- ジェネレーターUIでURL／UserScript／PowerShell／BAT連携を生成できる
- 改名後のリポジトリに旧エンドポイントパスが存在する
- `docs/MIGRATION.md` がGitHub Pages改名の影響を説明する
- 取得可能なすべてのWikiページにリポジトリ内のMarkdown版がある
- READMEの利用にGitHub Wikiが不要になる
- 一般的なエンコードと日付のケースが検証される
- 非公開の業務情報や認証情報がコミットされていない
- 関係のないユーザーのローカル変更が維持される

最後に、次を含む簡潔な報告を提示してください。

1. 変更したファイル
2. アーキテクチャの概要
3. 互換性の状態
4. Wiki移行の状態
5. 実施したテスト／チェック
6. ユーザーが手動で行う必要のある残作業

明示的な指示がない限り、pushやリモートでの破壊的な操作を行わないでください。
